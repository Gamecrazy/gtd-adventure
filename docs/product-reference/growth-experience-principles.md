# GTD 成长体验原则

本文件记录 GTD OS 游戏化与成长体验设计的当前原则。它是后续概念、机制、文案和界面方案的判断基准，不是功能规格、计分规则或实施计划。

状态：核心体验目标与成长主体已经确认；明亮勇者冒险的整体视觉与情绪感受已确认为一期设计基线，当前继续游戏化包装与 UI 迭代，系统助手功能保留为二期。

## 体验目标

GTD OS 的成长体验需要同时建立三种感受：

1. **使命感**：用户能够感到当下的选择和行动与自己希望怎样生活有关。
2. **养成感**：长期使用 GTD 的过程中，用户能够看见自己正在形成稳定的能力、品格和生活方式。
3. **信任感**：用户通过系统持续兑现承诺，逐渐相信可以把未尽事宜交给 GTD，而不必一直记在脑中。

这里的“使命感”是体验目标，不是新增的用户可见 GTD 层级。界面和数据模型继续使用术语表中的规范词“目的”；“目的”回答为什么做这些事。

## 已确认的核心判断

### 用户本人是成长主体

养成体验所表现的不是虚拟宠物、外部角色或独立游戏世界的成长，而是用户本人在成长。

系统不应以角色升级代替人的成长。它应帮助用户看见真实选择和行动留下的证据，并理解自己正在成为怎样的人。

### GTD 是核心系统，游戏化是体验包装

游戏化不建立一套与 GTD 并行的任务系统。收集、理清、组织、回顾和执行仍然是产品的核心循环；目的、愿景、目标、关注领域、项目和下一步行动仍然是表达方向与承诺的核心结构。

所有 GTD 概念都可以获得游戏化的称谓、叙事、视觉和反馈包装。包装可以改变用户感知这些概念的方式，但不能改变概念的底层语义、状态或行为。每个游戏化概念都必须能够明确映射回唯一的 GTD 概念；是否在界面中同时显示两层称谓仍待设计。

当前一期确认的视觉与情绪方向是“幻想冒险中的勇士感”：用户进入的应当是一个有征途、誓约、任务卷轴、行囊和营地感的幻想世界，而不是企业控制台或现代科幻 HUD。风格偏向明亮、高明度、有希望和生命力，避免整体过于昏暗、古旧或沉重。

当前确认的组合是**勇者冒险包装 + 黎明圣骑界面**。叙事表达冒险者、探索、主线、当前目标、旅途与营地；界面保留象牙白、金蓝、盾徽、对称秩序与庄严明亮的任务卷轴。用户已明确纠正：不要航海包装，因此不再将航路、航标、船舱、停泊、母港或扬帆作为系统的叙事骨架。目标感受是“冒险的自由与开阔 + 骑士誓约的使命与可靠”；各概念的最终名称仍需逐项确认。

幻想包装可以帮助表达方向、旅程和成长，但不能掩盖真实状态、制造概念歧义或增加完成工作的阻力。包装用于导航、分类和反馈，不自动改写用户填写的项目名称、行动内容、地点或时间：例如“把手机充电器移到客厅”保持原意，不额外加入虚构动作或地点。勇士身份表达的是用户直面现实、作出选择并采取行动，不引入战斗数值或要求用户扮演虚构角色。

### 已确认的视觉基线：明亮勇者冒险

明亮勇者冒险是[当前工作台](../../index.html)已确认的视觉基线。后续包装和 UI 迭代以此为基线，不再主动重新发散整套风格。

本次确认的是整体感受：

- **明亮的幻想冒险**：开阔、有希望，有勇者探索与生活征途的感受；不采用航海或现代科技叙事。
- **黎明圣骑的界面语言**：延续象牙白、金色与皇家蓝，使用盾徽、卷轴与有秩序的布局，兼顾冒险感、使命感与可靠感。
- **轻便、清楚的真实操作**：幻想表达包裹真实的 GTD 内容，用户仍能直接看懂当前事项、状态和下一步操作。

这次确认不等于逐项批准原型里的候选名称、示例数据、状态表达、布局细节或交互，也不表示原型已经达到完整产品的可用性标准。后续在这一基线上逐页打磨，并按桌面一屏规则验证；具体概念映射、功能与实施范围仍需逐步确认。

当前实现：[勇者冒险双语工作台](../../index.html) 采用已确认的视觉基线，默认英文并支持中文切换。五步入口对应实际页面，提供「收集 → 工作篮 → 理清 → 对应清单 → 执行」的基础原型流程，以及「选择行动 → 理解关联方向 → 完成 → 查看记录或恢复」闭环。回顾页仅提供回顾准备、记录查看和笔记，不将保存笔记计为完成每周回顾。深层编辑与完整 GTD 决策仍未展开。

该原型不连接正式系统，内置示例与用户在原型中输入的内容均只用于本地体验。具体布局、称谓和反馈仍待用户评估，不自动上升为已确认原则，也不扩展至二期助手。

### 用户是主角，GTD 是能力体系，助手是系统界面

产品采用类似爽文中“外挂系统”的关系结构，但不照搬其具体术语和套路：

- **用户是主角**：使命、选择、行动、后果和成长都属于用户。
- **GTD 是能力体系**：它把混乱转化为清晰的承诺、方向和下一步行动。
- **系统助手是能力的界面**：它让原本不可见的 GTD 逻辑、状态、风险和成长证据变得可感知，并在合适时机与用户对话。

助手不是被养成的宠物，也不替用户成长。它应当让用户产生“我获得了一套能够理解、托管和增强自己行动能力的系统”的感受。

“外挂系统”是当前用于描述产品体验的工作概念，不是已经确定的产品名称或用户可见术语。

### 助手服务于自主性与信任

系统助手可以解释状态、提示遗漏、组织证据、提出建议和反馈进展，但不能替用户决定人生目的、虚构成长，或在未经确认时把建议变成承诺。

当前确认的角色方向是“综合助手”，关系定位是“长期伙伴和私人参谋”。它不固定为单一的解说员、参谋或任务发布者，而是根据场景承担不同职责：

- 在用户需要了解现状时，解释状态、依据和变化；
- 在系统发现遗漏、风险或机会时，主动提出建议；
- 在方向和承诺已经由用户确认后，把下一步组织成具有推动力的任务表达；
- 在行动和阶段结束后，基于真实记录反馈结果并支持回顾。

综合不代表助手拥有无限权限。建议、任务表达和状态解释可以主动出现，人生方向与新增承诺仍由用户决定。

“长期伙伴”决定助手与用户的关系和时间尺度：

- 它持续记得用户确认过的目的、原则、愿景、承诺和重要变化；
- 它能够连接不同时期的选择，帮助用户看见长期成长而不只评价今天；
- 它理解人的生活会变化，允许暂停、返回、修正和放下；
- 它通过长期可靠的表现获得信任，而不是通过拟人化表演索取感情。

“私人参谋”决定助手的能力和权力边界：

- 它根据用户的真实背景与 GTD 状态提供个性化判断，而不是输出通用鸡汤；
- 它能够发现矛盾、遗漏、风险和机会，并坦诚提出不同意见；
- 它说明建议的依据、影响和不确定性，帮助用户作出决定；
- 它忠于用户确认的目的与原则，但不把顺从用户当成唯一目标；
- 最终决定权和承诺权始终属于用户。

长期伙伴不等于情感依赖，私人参谋也不等于命令者。助手既不能只会肯定和陪聊，也不能用“系统任务”的名义控制用户。

当前确认的基本语气是“温和但直率”：

- **温和**意味着理解用户所处的真实情境，不羞辱、不贴人格标签，也不把暂停、失败或改变方向简单解释为意志薄弱；
- **直率**意味着有证据时清楚指出矛盾、回避、失衡和可能后果，不用空泛鼓励掩盖问题，也不为了维持愉快气氛而回避不同意见。

温和负责维护长期关系，直率负责维护参谋价值。具体表达强度可以随场景变化，但两者都不能被取消。

助手的可信度来自：

- 知道什么，并能说明依据；
- 不知道什么，并明确承认边界；
- 记得用户已经交付给系统的承诺；
- 在正确的时机提醒，而不是持续打扰；
- 尊重用户的最终判断，不用奖励或惩罚操纵选择。

助手在什么场景切换职责、每种职责具有多强的主动性、是否使用生成式 AI，以及哪些具体动作必须由用户确认，仍需后续设计。

### 爽点来自掌控、洞察与成长

产品可以创造类似“系统觉醒”“能力解锁”和“阶段结算”的爽感，但核心满足应来自真实变化：

- 混乱的输入被理清，用户重新获得掌控感；
- 被遗忘的承诺在合适时机出现，系统证明自己值得托付；
- 日常行动与长期方向建立联系，用户看见行动的意义；
- 回顾揭示此前不易察觉的模式，用户获得对自己的新认识；
- 项目和人生状态真正发生改变，系统准确见证这段成长。

数值增长、稀有奖励或强烈动画不能替代这些真实爽点。

### 意义先于奖励

成长体验首先要回答以下问题：

- 我为什么选择做这件事？
- 它与我希望怎样生活、成为怎样的人有什么关系？
- 我最近通过哪些真实行动向那个方向靠近？

积分、等级、徽章、动画或其他奖励，即使以后采用，也只能服务于这些问题，不能成为产品目标本身。

### 成长来自真实证据

系统对成长的表达必须能够追溯到用户自己确认的方向和实际发生的 GTD 记录。建议理解为以下连续关系：

```text
目的与愿景
    ↓
目标与关注领域
    ↓
项目与承诺
    ↓
下一步行动
    ↓
回顾中可核对的成长证据
```

任务数量不等于成长。系统不能仅凭完成数量推断用户更自律、更优秀或更接近自己的目的，也不能擅自定义“更好的用户”。

### 信任通过可靠性获得

对 GTD 系统的信任不来自一个健康分数或鼓励文案，而来自反复得到验证的产品行为：

- 交给系统的内容不会丢失。
- 承诺会在合适的情境和时间重新出现。
- 项目缺少下一步行动、承诺长期未处理或系统出现偏航时，回顾能够把问题重新带回用户面前。
- 系统对状态、建议和成长的解释有真实数据依据，并允许用户核对。
- 数据不足时明确表示不知道，不伪造成长、连续性或完成历史。

### 回顾连接使命、养成与信任

回顾不是为了领取奖励，而是让用户重新看清：

- 最近的行动是否仍服务于自己的目的与愿景；
- 自己正在形成什么稳定倾向；
- 哪些承诺已经推进、停滞、改变或不再重要；
- GTD 系统是否完整、清晰并值得继续托付。

因此，回顾是三项目标汇合的关键体验，但具体如何表现尚未确定。

## 当前阶段边界

### 一期：游戏化包装与 UI 迭代

当前工作只聚焦于：

- 为现有 GTD 概念建立一致、可理解的游戏化包装；
- 确定产品的视觉语言、信息层级、交互反馈和情绪基调；
- 在不改变 GTD 底层语义的前提下，逐步迭代现有页面；
- 优先使用已有真实状态和数据表达系统感，不伪造尚不存在的智能能力；
- 每次只对齐并验证一个有边界的 UI 方向，再扩展到其他页面。

一期不实现系统助手的对话、长期记忆、主动分析、任务建议或代理操作。界面可以为二期保留一致的视觉语言和承载位置，但不能让用户误以为助手已经拥有这些能力。

### 二期：综合助手

系统助手的已确认原则继续保留，作为二期输入：综合助手是用户的长期伙伴和私人参谋，采用温和但直率的基本语气，并根据场景承担状态解释、主动建议、任务表达和回顾职责。

二期开始前再逐步确认助手的记忆、主动性、权限、实现方式、人格和交互形态；当前不继续细化，也不把候选助手功能纳入一期验收范围。

## 设计边界

后续方案不得：

- 用完成任务的数量代替使命、成长或价值判断。
- 为了游戏机制要求用户维护第二套任务、属性、货币或进度数据。
- 让助手成为真正的主角，或者让用户转而照顾、喂养和服务助手。
- 刻意制造用户对助手的情感依赖，或把持续使用产品包装成忠诚义务。
- 只为取悦用户而肯定所有选择，回避有依据的提醒和不同意见。
- 让助手以全知口吻陈述没有数据依据的判断。
- 让助手未经用户确认就定义人生目的、增加承诺或改变重要方向。
- 通过扣分、连续记录归零、羞辱性文案或失去虚拟资产制造焦虑。
- 奖励无意义的任务拆分、重复切换状态或为了得分而增加系统活动。
- 用系统推断替代用户对目的、愿景和重要性的自主判断。
- 用虚构叙事掩盖缺失、不完整或证据质量不足的数据。
- 让游戏包装干扰 GTD 决策，或把编辑、理清、回顾等主要操作推到首屏之外。

## 后续设计的判断问题

提出任何成长或游戏化方案时，先回答：

1. 它主要增强使命感、养成感还是信任感？
2. 它表现的是用户的真实成长，还是一个替代用户成长的外部数字或角色？
3. 它能否追溯到用户确认的方向和实际 GTD 记录？
4. 它是否帮助用户理解并相信系统，而不是只刺激用户点击？
5. 它会不会诱导刷量、制造焦虑或增加第二套维护负担？
6. 助手是在增强用户的判断和行动能力，还是在替用户作主？
7. 游戏化概念能否明确映射回真实的 GTD 概念和状态？
8. 关闭这层包装后，GTD 的语义和核心流程是否仍然完整？

无法清楚回答这些问题的方案，不进入界面或实施设计。

## 尚未确认

以下内容仍是开放问题，不属于当前原则或一期已批准方案：

- 成长应主要通过身份、人生领域，还是现有的目的—愿景—目标层级来表达。
- 是否采用积分、等级、里程、成就、连续性或健康状态。
- 二期系统助手的正式名称、具体人格和视觉形象。
- 二期“温和但直率”在普通提醒、明显偏航、长期停滞和高压力状态中的表达强度。
- 二期长期记忆如何形成、修正、遗忘并向用户解释。
- 二期综合助手在不同 GTD 阶段和用户状态下如何切换解说、参谋、任务表达与回顾职责。
- 二期综合助手主动介入的触发条件、频率、打扰边界和确认边界。
- 二期系统助手由确定性规则、生成式 AI，还是两者协作实现。
- “系统提示、状态面板、任务发布、阶段结算、能力解锁”等爽文式表达中，哪些适合本产品。
- 每一个 GTD 概念如何映射到游戏化包装，以及界面是否同时显示原始称谓。
- 地图、路线、罗盘、营地等幻想视觉隐喻分别应承载哪些 GTD 概念。
- 如何定义和汇总“成长证据”。
- 如何在日常执行、项目和每周回顾中呈现成长。
- 游戏化是否默认开启，以及需要哪些强度或关闭选项。
- 一期首个页面范围和游戏化包装的验证标准。
- 后续数据模型、完整界面范围、实施顺序和成功指标。

这些问题应逐步对齐理念后再设计，不从概念直接跳到完整机制。
